# 토스뱅크 - Privacy Operations Specialist 포트폴리오

개인정보 동의 관리 프로젝트 ‘동의ON’에서 기업별 동의항목 조회 API와 위험도 계산 모듈의 검증을 맡았습니다.

## 동의ON - 필수 동의와 사용자의 선택 동의 구분

기존 화면은 예시 데이터로 기업별 동의항목을 표시했습니다. 기업의 전체 동의항목과 사용자의 선택 기록을 함께 조회하는 API를 구현했습니다.

필수 항목은 항상 체크 상태로 반환하고, 선택 항목은 사용자가 실제로 체크한 기록을 반영했습니다. 각 항목에 민감도, 외부 제공, 보유기간, 처리 목적, AI 활용 관련 값도 함께 담았습니다.

당시 PR에는 필수 항목 처리, 선택 기록 반영, 다섯 변수 매핑을 확인한 서비스 테스트 3개가 통과했다고 기록했습니다. 전체 실행에서는 기존 백엔드 초기화 테스트 1개가 실패했습니다.

- [동의항목 조회 API와 테스트 - PR #21](https://github.com/dayeon053/dynamic-consent-system/pull/21)

## 동의ON - 위험도 산출값과 저장값 대조

개인정보처리방침에서 추출한 값이 위험도 등급으로 변환되는 과정에서 계산식, 등급 경계, 입력 누락과 저장 형식을 점검했습니다.

계산 모듈의 점수와 DB의 숫자 형식이 달라 소수 둘째 자리까지 변환하는 함수를 추가했습니다. 등급 이름을 매핑하는 방식과 빈 입력의 처리 기준은 백엔드 통합 가이드에 적었습니다.

당시 PR에는 공용 모델 테스트 28개가 통과했다고 기록했습니다. 동의 철회 전후의 점수 차이와 5개 등급의 경곗값도 확인했습니다.

- [계산과 저장 변환 회귀 테스트 - PR #20](https://github.com/dayeon053/dynamic-consent-system/pull/20)

화면과 서버에서 같은 선택 내역의 점수가 달라지는 경우도 확인했습니다. 화면은 위험 요인별 최댓값을 조합했고, 서버는 각 항목의 계산 결과 중 최댓값을 골랐습니다. 두 계산 방식이 다른 값을 내는 사례를 테스트로 재현하고 개인 맞춤 위험도 계산을 팀에서 정한 방식으로 통일했습니다. [계산 기준 통일 - PR #30](https://github.com/dayeon053/dynamic-consent-system/pull/30)

## 마이데이터 - 원본 만료와 합성 전환

3인 팀에서 보유기한이 지난 원본을 어떻게 처리할지 정책 요건을 정리하고 개념검증(PoC)에 참여했습니다. 팀은 원본의 만료 상태를 판정하고 CTGAN으로 합성데이터를 생성한 뒤 SQLite에 저장하는 흐름을 구성했습니다. 보고서에서 비교한 여러 모델 중 코드로 구현한 것은 CTGAN입니다. 원본과 합성데이터는 KS-test로 분포를 비교했고, 접근권한 구분은 설계 단계에서 검토했습니다.

## 개인정보 권한과 데이터 활용

- **INCOGNITO** - AI가 정보를 읽는 권한과 외부로 전송하는 권한을 구분하고, 민감한 실행 직전의 승인 및 전송 이력 기록을 개인 기획안에 담았습니다. 2인 팀에서 각자 제안한 내용을 통합해 발표하고 우수상을 받았습니다.
- **연합학습 개인 과제** - 서로 다른 세 노드의 로지스틱 회귀 모델을 가중평균했습니다. 네 노드로 확장하는 설계에는 차등프라이버시 적용 방안을 제안했습니다.
- **AI 모델 구성명세 분석** - 팀 프로젝트에서 모델 메타데이터와 의존성을 수집하는 모듈, API 오류 시 규칙 기반 대체 처리와 모듈 통합을 맡았습니다. 개발 당시 기록에서 테스트 완료는 확인되지 않았습니다.

## 금융 서비스와 인증

**nodown**은 장기할부 서비스 중단 뒤 할부항변 신청에 필요한 정보를 정리하는 시제품입니다. 4인 팀에서 거래 탐지, 가맹점 상태 모의조회, 사례 API, 기본요건 판단 코드를 맡았습니다. 서비스 이용 여부가 비어 있으면 추가자료 확인을 요청하고, 결제금액 등 기준에 미달하면 이유를 표시했습니다. 팀이 합성 거래 12건으로 확인한 결과 기본조건 충족은 7건, 폐업 알림 대상은 4건이었습니다. 최종 인정 여부는 카드사가 판단합니다. [조건 판정 코드](https://github.com/10502R/nodown/blob/main/services/rule_service.py) / [조건별 테스트](https://github.com/10502R/nodown/blob/main/tests/test_rule_service.py)

**캠퍼슈**에서는 학번과 이메일을 SQLite 학생 정보와 대조하고 결과를 안내하는 방식을 정리했습니다. 로그인과 회원가입은 3인이 공동 개발했습니다. 로컬 DB를 사용한 시제품으로, 학교 서버를 통한 재학 확인은 검증 범위에서 제외했습니다.

## 분석 환경과 기술 검증

**클라우드 SBOM/SCA** 프로젝트에서 저장소 주소를 S3로 전달하고 Lambda와 SSM을 통해 EC2에서 소프트웨어 구성명세를 생성하는 흐름을 맡았습니다. 팀이 저장소 입력에서 분석 결과 조회까지 시연했으며, 조회 화면과 취약점 조회 API는 다른 팀원의 담당 범위였습니다.

**LogosFuzz**에서는 컴파일 옵션과 API 정보를 테스트 프로그램 생성기에 연결했습니다. 평가용 정답 목록을 만들 때 헤더 검색 경로가 전달되지 않아 libsndfile의 92개 파일 중 70개가 컴파일에 실패했습니다. 옵션 전달을 수정한 뒤 선정한 API 8개를 라벨 및 컴파일 결과와 대조했습니다. 당시 PR의 전체 테스트 결과는 1,142개 통과, 5개 건너뜀, 기존 실패 6개였습니다. [수정 내용과 평가 기록 - PR #76](https://github.com/sesezz/LogosFuzz/pull/76)
